    Modelo-Vista-Controlador (MVC): Separación de capas

    Modelo

    Encapsula el estado de la aplicación, las entidades de dominio y la lógica de negocio fundamental. Define las reglas de validación y persistencia de datos.

    Vista

    Gestiona la representación visual de los datos al cliente. En arquitecturas de API modernas, actúa como la capa de serialización (ej. JSON/XML) en lugar de plantillas HTML.

    Controlador

    Actúa como intermediario: intercepta las peticiones de la red, invoca la lógica de negocio del modelo y selecciona la representación de respuesta adecuada.

    Singh et al. (2018, pp. 199-200).

    Riesgos arquitectónicos comunes
    
      
      
        
    • Controladores acoplados: Concentran validaciones de entrada, lógica de dominio y persistencia, dificultando el mantenimiento.
      • 
        
    • Modelos anémicos: Entidades reducidas a contenedores de datos (getters/setters) sin lógica de dominio propia.
      • 
        
    • Falta de encapsulamiento: Delegar validaciones críticas al cliente expone vulnerabilidades de seguridad.
      • 
      
    
      
    Consideración técnica: Aunque MVC independiza responsabilidades y facilita las pruebas unitarias, la aplicación se despliega como una unidad monolítica salvo que se estructure sobre microservicios.

    Diferenciación conceptual: Endpoint, Servicio y Contrato
    
  
    
    
    Endpoint
    La dirección de red (URL/URI) mediante la cual se expone una interfaz de comunicación.
    https://api.agendaya.co/v1/citas
    
    
    Servicio Web
    La funcionalidad técnica expuesta por un sistema para ser consumida de forma remota mediante protocolos estándar.
    
    
    Contrato de Servicio
    Especificación formal e inmutable que define las operaciones, estructuras de entrada/salida, errores y esquemas de seguridad.
    
  
    
  
    
    
    
      
    Roles en la arquitectura de integración
    
      
    El Proveedor publica la interfaz y garantiza el cumplimiento del contrato. El Consumidor ejecuta solicitudes orientadas al contrato expuesto.
    
    
    
    
    
      
    Especificación del contrato según el protocolo
    
      
    En SOAP el contrato se define explícitamente mediante esquemas XML (WSDL). En REST se formaliza habitualmente mediante la especificación OpenAPI.
    
    
    
  
    
  
    Singh et al. (2018, p. 208); OpenAPI Initiative (2021).

    REST: Restricciones de un estilo arquitectónico
    
  
    Formulado por Roy Fielding (2000), REST no constituye un protocolo, sino un conjunto de restricciones arquitectónicas para sistemas distribuidos.
    
  
    
    
    Desacoplamiento Cliente-Servidor
    Separa las responsabilidades de interfaz de usuario de las de almacenamiento de datos, permitiendo su evolución independiente.
    
    
    Sin Estado (Stateless)
    Cada petición debe contener la totalidad de la información requerida para ser procesada. El servidor no mantiene contexto de sesión entre peticiones.
    
    
    Capacidad de Caché
    Las respuestas deben declararse explícitamente como almacenables o no en caché para optimizar el rendimiento y reducir la latencia de red.
    
    
    Interfaz Uniforme y Sistemas en Capas
    Estandariza las interacciones mediante recursos y métodos HTTP, permitiendo la intermediación de proxies, gateways y balanceadores.
    
  
    
  
    Fielding (2000, cap. 5); Singh et al. (2018, p. 209).

    SOAP: Protocolo estandarizado de intercambio
    
  
    
    
    
      
    Simple Object Access Protocol (SOAP) define un marco de mensajería estricto basado en XML. Independiente del protocolo de transporte underlying (HTTP, SMTP, JMS).
    
      
    Garantiza interoperabilidad empresarial mediante la estandarización de contratos (WSDL) y políticas de seguridad/transaccionalidad en la cabecera del mensaje.
    
      
    Es el estándar predominante en sectores como banca, salud y entidades gubernamentales que requieren contratos rígidos y no repudiabilidad.
    
    
    
    
    
      
    
        
    Caso de aplicación nacional: Facturación Electrónica DIAN
    
        
    La Dirección de Impuestos y Aduanas Nacionales (DIAN) en Colombia exige el uso de servicios web SOAP 1.2 con WS-Security para la transmisión y validación previa de comprobantes electrónicos (operaciones SendBillSync y GetStatus).
    
      
    
      
    
        
    Integración en la arquitectura
    
        
    En el ecosistema AgendaYa, la emisión del comprobante fiscal requiere consumir de forma obligatoria el servicio SOAP regulado por la DIAN.
    
      
    
    
    
  
    
  
    Singh et al. (2018, p. 208); W3C (2007); DIAN (2018, 2021).

    CriterioSOAPREST
    
    
      
    NaturalezaProtocolo estandarizado de mensajeríaEstilo arquitectónico basado en recursos
    
      
    Formato de datosExclusivamente XML (Sobre Envelope)Flexibilidad (JSON, XML, HTML, Plain Text)
    
      
    Definición de ContratoMandatorio mediante WSDL / XSDOpcional mediante OpenAPI / Swagger

    Conclusiones e implicaciones de diseño
    
  
    
    
    Complementariedad Tecnológica
    SOAP y REST responden a necesidades de integración distintas. SOAP prioriza el rigor del contrato y la seguridad a nivel de mensaje; REST prioriza la eficiencia, el desacoplamiento y la simplicidad.
    
    
    Condicionamiento de Entorno
    La selección arquitectónica a menudo viene determinada por sistemas legados o normativas externas (ej. DIAN o sector financiero), exigiendo que el desarrollador domine ambos paradigmas.
    
    
    Prioridad del Diseño Interno
    La separación clara de responsabilidades mediante MVC y una capa de servicio bien estructurada constituye el requisito previo para exponer servicios web mantenibles.
    
    
    Seguridad Rigurosa
    La autenticación en servicios web debe basarse en protocolos robustos (OAuth 2.0 / TLS / WS-Security). El envio de credenciales simples en payload sin cifrado de transporte representa un riesgo crítico.
    
  
    
  
    Síntesis profesional: La evaluación y fundamentación crítica de arquitecturas de software sigue siendo una competencia central del ingeniero, orientada por los requerimientos no funcionales del sistema.
